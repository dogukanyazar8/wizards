Expo kararı

Expo bizi yavaşlatıyor mu?

Kısa cevap: şu aşamada Expo'da kalınmalı

karar

Expo SDK 56, React Native 0.85 ve React 19.2 çizgisinde modern bir yığın veriyor. Projede `expo-dev-client`, `@livekit/react-native`, `react-native-webrtc`, bildirim, secure-store, image/document picker ve EAS profilleri zaten var. Bu, ürün hedefleri için Expo Go sınırını aşan doğru yoldur.

Yavaşlatan nokta framework değil, ispat yükü

risk

Mobilde yavaşlık daha çok şuradan geliyor: tek dosyada büyüyen ürün kabuğu, native özelliklerin kullanıcı akışına tam bağlanması, cihaz matrisi, performans ölçümü, push/voice/media lifecycle ve release evidence eksikleri. Bunlar bare RN veya Swift/Kotlin'e geçince otomatik çözülmez.

Web platformu

Durum: B+ / 81

Web Whispr'ın ana ürün motoru. Graphify merkezleri auth, API, socket, locale, voice, DM ve workspace servislerinin yüksek fan-out taşıdığını gösteriyor.

API route dosyası 99
E2E spec dosyası 13
Next.js 15.5
React 19.1
Realtime Socket.IO

Yapılanlar

done
  • Mutating API isteklerinde CSRF origin/referer/sec-fetch-site kontrolü var.
  • CSP, frame-ancestors none, object-src none ve prod upgrade-insecure-requests kullanılıyor.
  • JSON body 1 MB ile sınırlı ve non-JSON mutating body reddediliyor.
  • Redis tabanlı Lua rate limit atomic çalışıyor.
  • Aktif kullanıcı kontrolü banned, deleted ve email verified durumlarını ayırıyor.
  • Health/readiness DB ve Redis'i 1 saniye timeout ile kontrol ediyor.

Başlıca riskler

risk
  • Playwright smoke geçmişinde login, settings, messaging ve server create akışları flaky.
  • CI loglarında web server Node heap OOM ve ECONNRESET görüldü; bu performans ve güvenilirlik riski.
  • Coverage threshold'ları düşük tutulmuş; kritik modüller için gerçek kalite sinyali sınırlı.
  • Gerçek Google OAuth, Resend, Turnstile, UploadThing, GIPHY ve LiveKit staging testleri otomatik değil.

Önerilen aksiyonlar

next
  • E2E web server'ı mümkünse `next build && next start` profiline taşı; `pnpm dev` kaynak tüketimini CI smoke için kullanma.
  • Smoke testlerde UI login ile API session bootstrap ayrımını netleştir; Turnstile/security proof bekleyen testler ayrı suite olmalı.
  • Auth, messaging, socket ve upload için negatif testleri artır; sadece happy path smoke yeterli değil.
  • Axe accessibility smoke ve Playwright screenshot/visual regression suite ekle.
  • Firefox/WebKit için küçük bir smoke matrisi kur; tam suite Chromium'da kalabilir.

Performans ve kaynak tüketimi

next
  • Railway maliyeti için ilk ölçüm noktası web process heap, socket connection count, Prisma query süreleri ve Redis memory olmalı.
  • Readiness cache iyi bir başlangıç; pahalı endpointlerde benzer cache/backpressure politikası gözden geçirilmeli.
  • Socket event fan-out ve unread/presence broadcast akışları yük testiyle doğrulanmalı.
  • Mesaj, DM, reaction ve attachment query path'lerinde N+1 ve geniş include riskleri düzenli profil edilmeli.

next

Mobile platformu

Durum: C+ / 67

Mobil uygulama Expo ile doğru yönde ilerliyor, fakat modern Discord/Slack düzeyi için native akışların ürün kanıtı, cihaz otomasyonu ve mimari modülerlik artmalı.

Expo SDK 56
React Native 0.85.3
React 19.2.3
Mobile test scripti 40
Root screen dosyası 11.183 satır

Yapılanlar

done
  • Expo SDK 56, Expo Dev Client, EAS build profilleri ve native modül temeli kurulmuş.
  • Mobile env release URL guard'ları HTTP/local/invalid hostları non-dev profillerde reddediyor.
  • API client relative path, timeout, JSON content-type ve bearer token akışını güvenli sınırlıyor.
  • Bootstrap gerçek `/api/v1/mobile/bootstrap` payload'unu Zod schema ile doğruluyor.
  • Realtime client `socket.io-client` ile channel, DM, voice, typing ve notification eventlerini dinliyor.
  • LiveKit mobile voice hook'u join, mute, camera, audio output, heartbeat ve participant merge akışlarını içeriyor.
  • Bildirim, mikrofon, kamera, fotoğraf ve document picker permission istekleri kullanıcı aksiyonundan sonra çalışıyor.

Expo değil, mimari merkezileşme yavaşlatıyor

risk
  • `mobile-root-screens.tsx` 11.183 satır; bu hız, review, regression ve ownership açısından ana darboğaz.
  • Tek dosyada navigation, state orchestration, realtime timers, voice, DM ve workspace akışları birleşiyor.
  • Bu yapı yeni özellik eklemeyi riskli hale getirir; küçük UI değişikliği bile geniş regression alanı yaratır.
  • Expo'dan çıkmak yerine feature slice ve hook/component ayrıştırması daha yüksek getiri sağlar.

Eksik ürün kanıtları

risk
  • Contract test sayısı iyi, fakat gerçek iOS/Android cihaz E2E ve store-grade UAT kanıtı yetersiz.
  • Push token registration kodu var; delivery, revoke, logout cleanup ve server lifecycle için uçtan uca kanıt gereklidir.
  • Voice join/mute/camera kodu var; düşük ağ, background, izin reddi, reconnect ve battery davranışı test edilmeli.
  • Document picker ve media permission runtime var; upload pipeline ve mesaj composer entegrasyonu tamamlanmalı.
  • Screen share mobilde unsupported; ürün vaadi buna göre açık ve dürüst kalmalı.

Önerilen aksiyonlar

next
  • `mobile-root-screens.tsx` dosyasını route/screen bazlı parçalara böl: home, DM, channel, voice, settings, composer.
  • Realtime client için AppState foreground/background, reconnect, missed-event backfill ve bounded timers testlerini cihazda koştur.
  • Voice için LiveKit UAT matrisi kur: izin reddi, join, mute, camera, audio output, disconnect, heartbeat cleanup.
  • Push için token registration, logout/revoke cleanup ve server delivery contract'ını tamamla.
  • Composer'a attachment upload, image picker/document picker ve hata durumlarını web parity ile bağla.
  • Startup, resume, composer latency ve idle memory bütçelerini EAS artifact olarak sakla.
